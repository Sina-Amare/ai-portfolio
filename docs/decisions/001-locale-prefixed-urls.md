# 001 — Persian lives at /fa URLs (locale-prefixed routing)

Status: accepted · 2026-09-26 · batch B3

## Context

English and Persian shared one URL; a `locale` cookie picked the language. Crawlers and link-preview
bots send no cookie, so Persian was never indexed or previewed, hreflang was impossible (it needs one
URL per language), and reading `cookies()` in the root layout made every page render per request.
The public URL structure is a contract: once search engines and shared links know it, changing it
means redirects forever. Hence this note.

## Decision

- English stays unprefixed (`/projects`), Persian is `/fa/...` (`/fa/projects`). `/en/...` 308s to the
  unprefixed URL, so there is exactly one English URL.
- All routes live in `app/[lang]/`. `proxy.ts` rewrites unprefixed requests to `/en/...` internally
  (the address bar never shows it) and passes `/fa` through.
- The language comes from the URL, never a cookie, so every public page is prerendered (SSG).
- Auto-detect only on entry: a GET/HEAD whose `Accept-Language` prefers `fa` is 307'd to `/fa`,
  except in-site navigation (`sec-fetch-site: same-origin`), bots (`isbot`), or when the `locale`
  cookie says otherwise. Only the language toggle writes that cookie.
- Each page sets its own canonical, `hreflang` en/fa/x-default (x-default = English), og:locale and
  explicit og/twitter images (`lib/seo.ts`). The sitemap lists both languages with alternates.

## Alternatives

- **Keep the cookie** — simplest, but Persian stays invisible to search and previews, and every page
  stays dynamic.
- **Prefix both languages** (`/en/...` and `/fa/...`) — symmetrical, but changes every existing English
  URL that is already indexed and shared.
- **next-intl** — does the same routing plus message formatting we don't need; about 100 lines of our
  own code (`lib/locale.ts` + `proxy.ts`) replace it without a dependency.
- **Subdomain** (`fa.sinaamareh.ir`) — needs DNS and a second Vercel domain for no extra benefit.

## Assumptions

- Two languages, English default. The helpers assume a single `/fa` prefix.
- Vercel runs the proxy before the CDN cache, so the per-visitor redirect and the cached static page
  don't conflict.
- `usePathname()` returns `/en/...` during prerender but the public path in the browser; anything
  rendered from the path must use `useBarePath()`.

## Known costs

- `notFound()` thrown from a page renders Next's error shell (`<html id="__next_error__">`: no
  lang/dir, nav or 404 text); the styled, localized 404 appears only after hydration. The status is
  still 404. Unknown `/projects/<slug>` already behaved this way. Unmatched URLs such as `/nope` are a
  regression: `app/not-found.tsx` used to server-render them, and now they go through the `[...rest]`
  catch-all, so without JavaScript they show a blank page. The 404 tab title is the home title. The
  way out for `/nope` is experimental `globalNotFound` (`app/global-not-found.tsx`), which skips the
  layout and so needs its own html, styles and fonts.
- Satori can't lay out Persian, so the `/fa` link-preview card is a committed screenshot
  (`app/[lang]/og-fa.png`, regenerated by `scripts/og-fa.mjs`).

## Revisit when

- A third language is added (move to a locale list in the proxy matcher and sitemap, maybe next-intl).
- Next ships a stable `global-not-found` or fixes page-level 404 SSR under a dynamic root layout, or
  anyone reports a blank 404 without JavaScript or a 404 crawl problem.
- Search Console reports hreflang errors or `/fa` pages as duplicates.
